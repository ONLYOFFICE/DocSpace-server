Tests of this change are vitest tests of the service (`common/ASC.AI.Chat/app/**/__tests__`,
`.claude/rules/ts-ai-tests.md`), with a fake sandbox gateway, a scripted model and stubbed portal routes: the
tools and the registry route live in ASC.AI.Chat only, and the C# integration suites cannot drive a model
round. A scenario whose outcome is the engine's (the pause for approval, a denied call), the portal's (the
plugin appears in `getWebPlugins`, a re-upload replaces a plugin, a saved file leaves the earlier ones as
they are) or the real sandbox's is not shown by these tests: those are seen in task 7.1. The branch moved the
lines one `verification.md` row cites (the README, task 2.3) and that row is updated.

## 6. Installation

- [x] 6.1 Implement `install_plugin`: argument check, the standing-permission checks of 6.2, the file read under the caller's rights, a multipart upload to `api/2.0/settings/webplugins` through the portal API client with the caller's forwarded headers, the answer relayed (name, version, `enabled` on 200; nothing installed on 400; not known on 403; possibly installed after a 5xx, an unreadable answer or a timeout); verify with the adapter tests for "Approved installation" (the upload and the answer), "Portal refuses the package", "Portal answers 403", "Portal's answer cannot be read", "File id that is not a positive integer" and "File that is not a readable archive". "New version of an installed plugin" and "appears in `getWebPlugins`" are the portal's and are seen in 7.1
- [x] 6.2 Keep `install_plugin` from running on a standing permission. The engine cannot hold that for one tool (`resolveAutoAllow` of `@onlyoffice/ai-chat`: "allow" asks nothing, "auto" skips a listed tool, and an approval with `allowAlways` writes the entry before it runs the call), so the adapter does (design.md decision 7): under "allow" it installs nothing, under "auto" with the tool listed it installs nothing and removes the entry. Verified with the adapter tests "installs nothing under the permission mode that runs every tool unasked", "installs nothing on a standing approval, takes it back, and installs when asked again", "installs nothing when the standing approval cannot be taken back" and "installs under the mode that asks for every call, whatever the list holds, and when no mode is stored". A per-tool "always ask" goes under "Known limitations" of the PR as a follow-up for the library

- [x] 6.3 "Pre-approving tools" is modified in its scenarios (a pre-approval of `install_plugin` does not last). Check the tests its TEST-CONFIRMED rows cite (`McpAllowAlwaysTests.cs`, `McpAllowAlwaysPauseTests.cs`, `McpRegisteredServerChatTests.cs`): none of them calls `install_plugin` (no file under `products/ASC.AI` names it), so they hold as they are; the new scenario is pinned at unit level by the adapter test of 6.2 and on a running portal in 7.1

## Where the server differs from the release notes or the OpenAPI document (spec follows the server)

| Release note / document | Server |
|---|---|
| v3.5 notes: "maximum number of plugins per portal 10 including system ones" | The configured maximum is 100 (`appsettings:396`) and the code default is 100 when the key is missing or `0`, a value outside 1–1000 moved to the nearest bound (`ConfigSettings:49`); the spec says 100. |
| v2.0 notes: "in SaaS only the system plugins from the CDN"; v2.0: plugin settings "do not work yet, only defaults apply" | Since v3.5 a hosted portal uploads its own plugins when the installation allows it (`Manager:276` checks only the config flag); the per-portal `settings` string is stored encrypted and returned (`Manager:953-998`). Only `system=true` stays standalone-only. |
| yaml `WebPluginDto.system`: "A system plugin cannot be deleted … only switched off"; yaml `PluginsDto.delete`: "plugins that ship with the installation cannot be removed regardless of this flag" | On a standalone installation with the delete flag on, `deleteWebPlugin` removes an installation-wide plugin from storage for every portal (`Manager:1014-1033`; v3.6 notes line 45). The texts describe the hosted case only. |
| yaml has no `PUT /api/2.0/settings/webplugins/{name}/refresh` | `Controller:264-282` publishes `refreshWebPlugin`; the contract of 2026-11-07 and the SDKs lacked it; the yaml of the SDK submodule now has it (68871-68896), and the integration tests call it raw (`Tests/WebPluginRefreshTests.cs`). Probably the contract was generated before the action was added. |
| yaml `WebPluginDto.name` example `Example Plugin` | A manifest name with a space or a capital letter is refused ("Wrong plugin name", `Manager:244, 382-385`); the example cannot be uploaded. |
| yaml `getWebPlugins` 403 "Web plugins are switched off" only | Also the generic authorization of the Web.Api (401 anonymous) — listed in the yaml as the standard 401 row; no settings right is demanded, so no "Access denied" 403 exists for the reads. Agrees. |

## Left out of the spec, and why

- **The editor add-on list** (`pluginsData` of the document editor configuration, `PluginsConfigDto` in
  `products/ASC.Files/Core/ApiModels/ResponseDto/EditorConfigDto.cs:228-250`): always empty, the building code is
  commented out; named in the Purpose only.
- **What a plugin does in the browser**: scopes, items, context-menu actions, pages/sections, localisation, CSS
  customisation, error display (v3.7, v4.0 notes), the plugin SDK package and the Playwright e2e coverage
  (`../tests/e2e-tests/src/objects/settings/integration/`): client behaviour, not the server.
- **A `settings/plugins` route**: none exists in the Web.Api; the switches are only the `plugins` block of
  `getSettings`. The proxy's `location ~* /plugins` (`nginx:633-635`, `$plugins_service_url`) points at a service
  outside this repository and is not part of `settings/webplugins`.
- **The Content Security Policy mechanics** beyond the domain list a plugin adds (header building, per-domain cache
  keys, standalone base domain): `CspSettingsHelper`, its own concern.
- **Rate-limit headers and 429 rows** of the yaml: generic policy.
- **The in-memory manifest cache and its cross-node reset** (`Manager:249-254, 778-792`): implementation; the
  refresh requirement describes its observable effect only.
- **The exact storage layout** (`$STORAGE_ROOT\Studio\{tenant}\webplugins\<name>\…`, `~/studio/webplugins`): configuration.
